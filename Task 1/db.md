# Сравнение векторных баз данных (ChromaDB vs FAISS)

## Что сравниваем

| Вариант | Что это | Лицензия | Где запускается |
| --- | --- | --- | --- |
| ChromaDB | Встраиваемая векторная база данных (embedded) | Apache 2.0 | локально в том же Python-процессе или как отдельный сервер |
| FAISS | Библиотека быстрого поиска по векторам (не база) | MIT | локально, как библиотека в коде |

## Сводная таблица сравнения

| Вариант | Скорость поиска и индексации | Сложность внедрения и поддержки | Удобство в работе | Стоимость владения |
| --- | --- | --- | --- | --- |
| ChromaDB | Быстрая на нашем объёме: поиск - единицы миллисекунд, индексация ~150 тыс. чанков занимает минуты | Низкая: `pip install chromadb`, персистентность и метаданные из коробки, минимум кода | Высокая: коллекции, встроенное хранение текста + метаданных + эмбеддингов, фильтры `where`, простая интеграция с LangChain/LlamaIndex | 0 руб (open source), меньше времени разработчика |
| FAISS | Самая быстрая на больших объёмах (sub-ms), но на 100-200 тыс. векторов выигрыш неощутим; на CPU без CUDA преимущество меньше | Высокая: это библиотека - персистентность, метаданные, CRUD, API нужно писать самому | Ниже: работа с numpy-массивами, ручной выбор индекса (Flat/IVF/HNSW/PQ), отдельное хранение текста и метаданных | 0 руб (open source), но заметно больше инженерного времени |

## Разбор по критериям

### 1. Скорость поиска и индексации

- FAISS - эталон сырой скорости ANN-поиска: на больших наборах (миллионы-миллиарды векторов) с IVF-PQ на GPU даёт субмиллисекундные задержки. Но это преимущество раскрывается на 100 тыс.+ векторов и с CUDA-ускорением.
- ChromaDB использует HNSW-индекс (похожий на FAISS-овский) и на нашем объёме 100-200 тыс. чанков возвращает результат за единицы миллисекунд - для RAG-чата это неотличимо от FAISS. По умолчанию recall около 84%, чего для RAG достаточно (ошибки сглаживает LLM или переранжировщик).
- Индексация: у ChromaDB встроенная (добавляешь документы - сохраняются сами), у FAISS - вручную (сам заполняешь массив и вызываешь index.add). По времени на 150 тыс. векторов обе справляются за минуты.
- Важный нюанс нашего железа: faiss-gpu работает только с NVIDIA CUDA, а у нас Apple M4 Pro. То есть главное преимущество FAISS (GPU) у нас не работает, остаётся faiss-cpu, где разрыв с ChromaDB ещё меньше.

Вывод: на нашем масштабе и железе практической разницы в скорости нет; FAISS быстрее только на больших объёмах с GPU, которого у нас нет.

### 2. Сложность внедрения и поддержки

- ChromaDB: одна команда `pip install chromadb`, всё из коробки - персистентность (SQLite + Parquet), метаданные, CRUD, клиент-серверный режим. Для MVP/RAG-бота пишется минимум кода.
- FAISS: это библиотека, а не база. Нужно самому реализовать сохранение/загрузку индекса (`write_index`/`read_index`), хранение исходного текста и метаданных в отдельном хранилище (например, SQLite/Postgres), связку id вектора с документом, обновление/удаление и crash recovery. Это больше кода и больше точек отказа.
- Поддержка: у ChromaDB обновление документов и переиндексация проще (обновляешь коллекцию), у FAISS придётся пересобирать индекс и следить за согласованностью с метаданными.

Вывод: по внедрению и поддержке ChromaDB заметно проще; FAISS требует строить вокруг себя слой базы данных.

### 3. Удобство в работе

- ChromaDB - "база для приложений": коллекции, встроенное хранение документов, эмбеддингов и метаданных, фильтрация `where={"source": "confluence/space-x"}` одной строкой. Удобно итерировать над чанкингом и стратегией поиска, что важно на этапе прототипа.
- FAISS - "движок для поиска": максимальный контроль над индексом и точностью (efSearch, PQ), но работать нужно с numpy-массивами и вручную связывать векторы с текстом. Для исследовательских/бенчмарковых задач - отлично, для приложения - лишняя ручная работа.
- Для персонализированного поиска (роли пользователей, фильтр по пространствам и типам документов) метаданные-фильтры ChromaDB - это реальный выигрыш: с FAISS их пришлось бы реализовывать отдельно.

Вывод: для приложения-бота удобнее ChromaDB; FAISS - инструмент для тонкой настройки поиска, а не готовое хранилище.

### 4. Стоимость владения (учёт инфраструктуры)

- Обе системы бесплатны и open source (ChromaDB - Apache 2.0, FAISS - MIT), лицензионных платежей нет.
- Инфраструктура: обе работают на уже имеющемся Mac M4 Pro, допзатрат на серверы нет. Память на 150 тыс. векторов - меньше 1 ГБ, уживается с Qwen3-14B и bge-m3 в 24 ГБ.
- Основная статья "стоимости" - время разработчика. FAISS экономит только на вычислительных ресурсах при очень больших масштабах, а платит инженерным временем на самодельную обвязку (персистентность, метаданные, API). ChromaDB экономит это время, отдавая чуть-чуть сырой скорости, которую мы всё равно не используем.
- Для нас важно: данные конфиденциальны, поэтому облачные managed-базы (Pinecone, Weaviate Cloud) не рассматриваются - обе локальные альтернативы бесплатны и не требуют оплаты за API.

Вывод: по стоимости обе бесплатны, но ChromaDB дешевле в пересчёте на трудозатраты; FAISS окупает свою сложность только на объёмах, которых у нас нет.

## Рекомендация по выбору векторной базы

### Вариант 1. ChromaDB (основной)

- Плюсы: персистентность и метаданные из коробки, фильтрация для персонализации, минимум кода, быстро прототипировать, локально и бесплатно, встраивается в процесс (или отдельным сервером при росте).
- Минусы: на очень больших объёмах (10M+ векторов) и под тяжёлыми нагрузками уступает tuned FAISS; recall по умолчанию ~84% (при желании поднимается настройкой HNSW или переранжированием).
- Подходит: наш кейс - корпоративный RAG-бот с фильтрами по ролям и источникам, объём ~100-200 тыс. чанков.

### Вариант 2. FAISS (библиотека, максимум контроля)

- Плюсы: самый быстрый сырой поиск, тонкая настройка индексов (IVF/HNSW/PQ), эталон для бенчмарков.
- Минусы: нет персистентности, метаданных и фильтров - всё писать самим; GPU-ускорение требует NVIDIA CUDA, которого нет на M4 Pro; крутая кривая обучения.
- Подходит: когда нужен предел производительности на миллионах векторов или исследовательская работа, а не готовое приложение.

### Вариант 3. Гибрид (ChromaDB сейчас, FAISS при росте)

- Плюсы: начать на ChromaDB (быстро), при необходимости перенести векторы в FAISS (векторы переносимы, переэмбеддинг не нужен) - решение не блокирует масштабирование.
- Минусы: запас на миграцию, но на нашем объёме он скорее всего не понадобится.

### Итоговая рекомендация

Для кейса QuantumForge Software выбираю Вариант 1 - ChromaDB как основную векторную базу.

Обоснование:

- Объём данных (100-200 тыс. чанков) целиком в зоне комфорта ChromaDB, а разницы в скорости с FAISS на таком масштабе и без CUDA нет.
- Нужна фильтрация по метаданным для персонализированных ответов (роли, пространства, типы документов) - у ChromaDB она из коробки, у FAISS её пришлось бы писать вручную.
- Персистентность из коробки критична: база знаний переживает перезапуск без самодельного save/load.
- Локально, бесплатно, open source (Apache 2.0), данные не покидают машину - соответствует требованиям конфиденциальности.
- Меньше инженерного времени и меньше кода = проще поддержка и быстрее итерации для проектной работы.
- Архитектурно заложить абстракцию над векторным хранилищем, чтобы при росте базы (миллионы векторов) можно было перейти на FAISS или Qdrant без переписывания пайплайна.
